Oracle 19c · partition maintenance on a busy table

Exchange, don't drop

Dropping a partition that no running query touches still invalidates every cursor on the table. When many sessions share that cursor, they all stall while one of them rebuilds it. EXCHANGE PARTITION removes the same data without disturbing them. This guide shows the mechanism, the test that measured it on a real 19c database, and every script that ran.

The setup

Table T has 400 range partitions of 1,000 rows each. Twenty-four sessions run one query over and over. The query reads only partition P1: its predicate id < 1000 lets the optimizer prune to that one partition when it builds the plan.

All 24 sessions share a single cursor in the library cache. That is normal and efficient: the statement is parsed once and executed thousands of times. A second session handles maintenance and removes the oldest data, in partition P400.

What a DROP does to a hot cursor

On 19c, ALTER TABLE t DROP PARTITION p400 UPDATE INDEXES invalidates the shared cursor, even though the cursor never reads P400. The DDL itself is quick: 17 to 33 ms in the test. The trouble starts at the next execution.

  • The first session to execute finds the cursor invalid and starts a hard parse. While it builds the new cursor it holds the cursor's pin in exclusive (X) mode.
  • Every other session needs the same cursor. Each one requests the pin in shared (S) mode, cannot get it, and waits on cursor: pin S wait on X.
  • Nobody runs the query until the hard parse finishes. Then the cursor is valid again and everyone continues.

The pile-up lasts as long as one hard parse. In the test, each hard parse was set to cost 2 seconds of CPU, roughly what a complex production statement can cost (why the test does that). With a cheap statement the pile-up is shorter, but it still happens on every drop and for every cursor that depends on the table.

What EXCHANGE does instead

ALTER TABLE t EXCHANGE PARTITION p400 WITH TABLE t_x INCLUDING INDEXES WITHOUT VALIDATION swaps the storage of partition P400 with the storage of an ordinary table T_X that has the same shape. No rows are copied. Oracle changes which segment each name points to in the data dictionary.

Since 12.2, Oracle checks whether a cursor is really affected by this kind of DDL (fine-grained cursor invalidation). The hot cursor reads only P1, so it stays valid. V$SQL.DDL_NO_INVALIDATE records this: X means a DDL changed a dependent object without invalidating the cursor, and the cursor has executed since.

Using it in production

To age out a partition on a busy table, swap it out first and dispose of the data separately. Nothing hot depends on the standalone table, so dropping it later disturbs nobody.

How the test works

The harness is a set of SQL*Plus/SQLcl scripts and one PL/SQL package, PINX_LAB. One call, pinx_lab.run_case('DROP' | 'EXCHANGE', …), runs a complete test. The two runs follow exactly the same steps and differ only in the DDL statement.

Deciding whether a particular DDL invalidated the cursor is harder than it sounds. Under load, every reparse builds the cursor in a different child slot, and the invalidated child disappears from V$SQL. Comparing INVALIDATIONS before and after the run therefore reported 5 invalidations for 10 drops. The harness instead takes a signature of every child of the hot cursor (address, loads, invalidations) just before each DDL and again just before the next one. If the two differ, that DDL invalidated the cursor.

Making the pile-up visible

ASH samples every active session once per second. A pile-up that lasts a fifth of a second usually falls between two samples. The first versions of the test showed exactly that. The workers' own counters recorded 36.6 s of cursor: pin S wait on X over 10 drops, while ASH recorded zero samples of it.

Two settings make the pile-up large and long enough to see, without changing what is being tested:

  • PARSE_MS (2000) sets how much CPU each hard parse of the hot query costs. The query carries a predicate pinx_parse_marker(a.id) >= 0, which is always true. The function has user-defined optimizer statistics. During every hard parse, the optimizer calls their selectivity function, and that function burns PARSE_MS of CPU. Executions never call it, so they stay cheap.
  • THINK_MS (20) makes each worker pause after every execution. Without a pause, 24 sessions keep both CPUs busy all the time, and ASH then reports every session as "ON CPU", waiting or not.

Configuration and drivers

The table and the hot query

build_table recreates T for every run. Explicit 64 KB extents matter: 19c gives each new partition an 8 MB initial extent, which would have made T about 3 GB.

The DDL under test

The controller forces cursor_invalidation = immediate (the 19c default) so that a system-level setting cannot change the outcome. Before each DDL it records the cursor's signature, which then serves as the "settled" state of the previous DDL.

Measuring the workers

Each worker snapshots its own counters with one INSERT … SELECT. Oracle parses that statement before it reads the counters, so the snapshot never counts its own parse. That is why Run B shows exactly 0 hard parses.

Run it yourself

  1. On a 19c test database, connect as a DBA inside the target PDB and run @admin/create_user.sql <password>. It creates the schema PINX with the direct grants the harness needs (roles do not work inside definer-rights PL/SQL or scheduler jobs).
  2. Run ./run.sh pinx@//host:1521/pdb run_all. It installs the harness, runs both cases, writes the evidence to reports/, and exits non-zero if any check fails. A full run takes 4 to 5 minutes.
  3. Open reports/pinx_timeline_r<A>_r<B>.html, and the ASH and AWR reports linked from it.
  4. Remove everything with ./run.sh … cleanup and, as a DBA, @admin/drop_user.sql.

ASH, AWR snapshots and the ASH/AWR reports need the Diagnostics Pack. With AWR = AUTO the harness uses them only when control_management_pack_access includes DIAGNOSTIC. The pass/fail checks rely on the sessions' own counters and need no licence.

Limits and caveats

  • The test box has 2 CPUs. On a bigger machine the hard parse competes less for CPU, but the pile-up still lasts as long as one hard parse, and every session that needs the cursor still waits.
  • The 2-second parse cost is deliberate (PARSE_MS). With PARSE_MS = 0, every DROP still invalidates the cursor and still causes waits that the counters prove, but each pile-up lasts only about 200 ms.
  • The hot query prunes statically to P1, a partition the exchange never touches. Queries that read the exchanged partition itself were not tested.
  • In a separate single-session probe, TRUNCATE PARTITION also left the cursor valid. Only DROP PARTITION invalidated it. The truncate case is not part of the automated checks.
  • Removing the emptied partition afterwards is a DROP PARTITION too. Schedule it for a quiet period, or keep empty partitions until one comes.
  • Measured on Oracle 19.27 only. The harness refuses older releases and warns on newer ones.
