DROP PARTITION and EXCHANGE PARTITION under concurrent load

On Oracle 19c, ALTER TABLE … DROP PARTITION invalidates every cursor that depends on the table, including cursors that do not read the dropped partition. ALTER TABLE … EXCHANGE PARTITION does not invalidate a query cursor that is statically pruned to another partition; it does invalidate an INSERT … VALUES cursor on the table. This page documents a test of both statements with 24 concurrent sessions that query one partition and insert into another: setup, measurements and scripts.

Test setup

Table T: 400 range partitions of 1,000 rows each, plus the current partition PCUR (VALUES LESS THAN (MAXVALUE)), empty at the start. 24 sessions run a loop:

  1. Execute the hot query. It reads only partition P1; the predicate id < 1000 allows static partition pruning to P1.
  2. Insert one row into T with an id from the sequence T_SEQ, which starts above P400's range, so every row goes to PCUR. Commit.
  3. Pause 20 ms.

The 24 sessions share one cursor for the query and one for the insert: one hard parse each, then repeated executions. A separate session issues the DDL against the highest partition below PCUR.

DROP PARTITION

On 19c, ALTER TABLE t DROP PARTITION p400 UPDATE INDEXES invalidates both shared cursors, although neither reads or writes P400. Elapsed time of the DDL in the test: 13–216 ms.

  • The next session that executes the query finds the cursor invalid and hard-parses it. During the hard parse it holds the cursor pin in exclusive (X) mode.
  • The other sessions request the pin in shared (S) mode and wait on cursor: pin S wait on X.
  • When the hard parse completes, the cursor is valid and the waiting sessions continue.
  • The insert cursor is re-parsed the same way, in a few milliseconds. ASH recorded 0 samples of sessions waiting for it.

The wait lasts as long as one hard parse. In the test, each hard parse of the hot query was set to 2 s of CPU (PARSE_MS). With a shorter hard parse the wait is shorter; it still occurs after every DROP, for every cursor that depends on the table.

EXCHANGE PARTITION

ALTER TABLE t EXCHANGE PARTITION p400 WITH TABLE t_x INCLUDING INDEXES WITHOUT VALIDATION swaps the segment of partition P400 with the segment of table T_X, which has the same columns and indexes. No rows are copied. The data dictionary is updated so that each name points to the other segment.

Since 12.2, Oracle determines for each dependent cursor whether this DDL affects it (fine-grained cursor invalidation):

  • Hot query cursor: statically pruned to P1, not invalidated. V$SQL.DDL_NO_INVALIDATE = X: a DDL changed a dependent object without invalidating the cursor, and the cursor has executed since.
  • Insert cursor: invalidated by every exchange (10 of 10). An INSERT … VALUES is not pruned to a partition at parse time. The re-parse takes a few milliseconds: the workers waited 43 times on cursor: pin S wait on X, 136 ms in total over the 10 exchanges, with 10 hard parses, one per exchange.

Production sequence

Sequence for removing a partition's data from a table under load: exchange the partition with an empty table, then drop or archive that table. No cursor on T depends on the standalone table.

The exchange leaves query cursors that are pruned to other partitions valid. DML cursors on T, such as the test's INSERT, are invalidated and re-parsed. With a short parse this costs milliseconds; a DML statement with an expensive parse was not tested.

Test harness

Five shell scripts, executed in order, using SQL*Plus or SQLcl and the PL/SQL package PINX_LAB:

  1. 1_build.sh: creates user PINX, installs the package, builds table T and the sequence T_SEQ.
  2. 2_start_workers.sh: calls pinx_lab.start_workers, which starts 24 scheduler jobs. Each runs the hot query, inserts a row into PCUR and commits, in a loop.
  3. 3_test_drop.sh: calls pinx_lab.run_case('DROP', …), one measured test against the running jobs.
  4. 4_test_exchange.sh: calls pinx_lab.run_case('EXCHANGE', …), the same procedure with a different DDL statement.
  5. 5_cleanup.sh: stops the jobs, drops the user.

Timings of steps 2 to 4, from the script output:

A comparison of V$SQL.INVALIDATIONS before and after a test undercounts under load. With 24 sessions, each reparse creates the cursor in a different child slot and the invalidated child leaves V$SQL; the before/after comparison reported 5 invalidations for 10 drops. The harness records a signature of every child of the hot query cursor and of the insert cursor (address, loads, invalidations) before each DDL and again before the next DDL. A changed signature means that DDL invalidated the cursor.

ASH sampling and wait duration

ASH samples active sessions once per second. A wait of 0.2 s is usually not sampled. In early versions of the test, the workers' counters recorded 36.6 s of cursor: pin S wait on X over 10 drops, and ASH recorded 0 samples of that event.

Two settings increase the duration of the waits. Neither changes how the DDL affects the cursor:

  • PARSE_MS (2000): CPU time of each hard parse of the hot query. The query contains the predicate pinx_parse_marker(a.id) >= 0, which is always true. The function has user-defined optimizer statistics. During each hard parse the optimizer calls their selectivity function, which uses PARSE_MS of CPU. Executions do not call it.
  • THINK_MS (20): pause after each execution. Without it, 24 sessions saturate both CPUs, and ASH reports waiting sessions as "ON CPU".

Scripts

Excerpts from the project files, with line numbers. Main components: setup.sql (tables, package PINX_LAB, report views), five shell scripts, several SQL driver scripts.

Commands

Commands executed on the database host, in the project directory. The password was supplied in the environment variable PINX_PASSWORD; without it, each script prompts for it.

Configuration and drivers

Table and hot query

build_table (step 1) creates T with 64 KB extents. The 19c default initial extent for a new partition is 8 MB, which would give T a size of about 3 GB. It adds the current partition PCUR and the sequence T_SEQ, which starts above the last partition's range.

Workers

start_workers (step 2) creates one scheduler job per worker. Each job runs pinx_hot_loop: execute the hot query, insert INSERTS rows into PCUR and commit, then read the one-row table PINX_CTL (RUN, MEASURE or STOP). A test changes PINX_CTL; each worker takes its counter snapshot when the value changes. Each test checks that all workers are running before it starts.

DDL

The controller sets cursor_invalidation = immediate (the 19c default) in its session, so a system-level setting does not affect the result. The cursor signatures recorded before each DDL are also the settled state of the previous DDL. After each DDL it prints what the workers are doing 0.5 s later, the row counts, and whether each cursor was invalidated.

Worker counters

Each worker snapshot is one INSERT … SELECT. The statement is parsed before it reads the counters, so the snapshot does not count its own parse. The EXCHANGE test therefore shows only the insert's hard parses, one per exchange (0 with INSERTS = 0).

Checks

The pass/fail checks are a view. The comment at its top explains how the EXCHANGE checks allow for the insert's re-parses.

ASH, AWR snapshots and the ASH/AWR reports require the Diagnostics Pack. With AWR = AUTO they are used only when control_management_pack_access includes DIAGNOSTIC. The pass/fail checks use session counters and require no licence.

Limitations

  • Test host: 2 CPUs. With more CPUs the hard parse has less CPU contention; the wait still lasts one hard parse and affects every session that executes the cursor.
  • The parse cost of 2 s is set by PARSE_MS. With PARSE_MS = 0, every DROP still invalidates the cursor and causes waits recorded in the session counters; each wait lasts about 200 ms.
  • The hot query prunes statically to P1. Queries that read the exchanged partition were not tested.
  • The insert is a single-row INSERT … VALUES with a parse of a few milliseconds. Every EXCHANGE invalidated it. A DML statement with an expensive parse was not tested; after an exchange it would also be re-parsed.
  • TRUNCATE PARTITION did not invalidate the cursor in a separate single-session test. It is not part of the automated checks.
  • Dropping the empty partition after the exchange is a DROP PARTITION and invalidates dependent cursors.
  • Measured on Oracle 19.27 only. The harness refuses older releases and warns on newer ones.
